# Описание

Первый проект по МК в котором пытаюсь разобраться в устройстве МК путем написания собственного HAL

# 1. Общие принципы

Проект представляет собой разработку собственной C++ библиотеки для программной абстракции над аппартным интерфейсом STM32F401CCU6.

Разработка ведётся по принципу: **одна задача → одна issue → отдельная ветка → реализация → проверка → Pull Request → Merge**.

# 2. `Guidline` документирования

Каждый класс и функция должны быть задокументированы в формате `Doxygen`

Я буду каждую неделю обновлять документацию

# 3. `Guidline` оформления Issue

### Название

Используется формат:

`[МОДУЛЬ] Краткое описание действия`

Примеры:

- `[RCC] Реализовать управление тактированием GPIO`
- `[GPIO] Реализовать конфигурацию цифрового выхода`
- `[GPIO] Реализовать атомарное изменение состояния вывода`
- `[SYSTICK] Реализовать миллисекундный системный счётчик`

Название должно отражать конкретный результат, а не общий процесс изучения технологии.

### Обязательные разделы

**Цель**

Краткое описание требуемой функциональности и причины её реализации.

**Функциональные требования**

Перечень возможностей, которые должны появиться после выполнения задачи.

**Технические требования**

Аппаратные и программные ограничения: используемые регистры, стандарт C++, требования к безопасности операций и совместимости.

**Критерии приёмки (Definition of Done)**

Проверяемые условия, при выполнении которых Issue можно закрыть.

**Ограничения задачи**

Что намеренно не входит в текущую реализацию, чтобы избежать неконтролируемого расширения объёма работы.

# 4. `Guidline` оформления Pull Request

### Название

`[МОДУЛЬ] Краткое описание реализованного изменения`

Например:

`[RCC] Реализовано управление тактированием GPIO`

### Обязательные разделы

**Связанная задача**

Ссылка на Issue с использованием `Closes #номер`.

**Что реализовано**

Краткое описание фактически выполненных изменений. Перечисляются новые возможности и затронутые компоненты.

**Техническая реализация**

Описание существенных инженерных решений:

- Какие регистры или аппаратные механизмы используются.
- Как организованы классы и их ответственность.
- Какие битовые операции и правила доступа применяются.
- Какие особенности оборудования учтены.

**Обоснование решений**

Почему выбран именно этот подход, какие альтернативы рассматривались при необходимости и какие ограничения он имеет.

**Проверка**

Перечень реально выполненных проверок: сборка, прошивка, аппаратное тестирование, автоматические тесты.

**Ограничения и известные проблемы**

Что пока не поддерживается, какие риски остаются и что будет реализовано в следующих задачах.

# 5. `Guidline` именования веток и коммитов

### Названия веток

`тип/номер-issue-краткое-название`

Примеры:

- `feature/3-rcc-clock-control`
- `feature/4-gpio-config`
- `fix/8-gpio-register-mask`
- `refactor/12-register-access`

### Сообщения коммитов
`тип(модуль): действие`

Примеры:

- `feat(rcc): Реализовал включение тактирования GPIO` 	
- `feat(gpio): Реализовал настройку режимов пинов`
- `fix(gpio): Исправил маску для установки битов регистров`
- `refactor(rcc): разделил адреса регистров в классе`
- `docs: Обновил описание архитектуры`
- `build: настроил цепочку сборки`

Основные типы: `feat`, `fix`, `refactor`, `docs`, `test`, `build`, `chore`.

Коммит должен объединять логически связанные изменения.


# 6. `Guidline` выполнения задачи 	

1. Выбрать `Issue` и переместить его в `In Progress`.
2. В `Issues` создать ветку по кнопке `Development` справа, сформировав корректное название ветки в соответствии c `5. Guidline именования веток и коммитов`
3. Реализовать функциональность согласно требованиям.
4. Собрать проект и выполнить необходимые проверки.
5. Создать коммиты и отправить ветку на `GitHub`.
6. Открыть `PR`, заполнить описание в соответствии с `4. Guidline оформления Pull Request` и связать с `Issue`.
7. Проверить изменения и выполнить `Merge`.
8. Убедиться, что `Issue` закрыт, и обновить локальную `main`.

# 7. Особенности embedded-разработки

Для изменений аппаратных драйверов дополнительно проверяются:

- Правильность адресов и битовых полей регистров.
- Корректность доступа к MMIO через `volatile`.
- Сохранение посторонних битов при изменении регистра.
- Соблюдение требований по тактированию периферии.
- Соответствие реализации документации STM32.
- Поведение на реальном устройстве, когда такая проверка необходима.
- Начальное состояние периферии после сброса.

При использовании зависимостей от конкретной модели STM32 необходимо явно указывать поддерживаемые микроконтроллеры.
